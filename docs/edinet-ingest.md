# EDINET 全社取り込み — 作業ドキュメント

層1（数値）を EDINET API から全上場企業ぶん取り込むための作業メモ。
**次に触る人（人でもAIでも）がここだけ読んで続けられる**ことを目的にする。

設計の背骨は `../CLAUDE.md`、全体設計は `ARCHITECTURE.md`、現状は `HANDOFF.md`。

---

## 1. 何のためにやるか

いま層1（`agent/data/facts/`）が点いているのは **2社だけ**（7561=31件 / 5071=10件）。
これを EDINET の有価証券報告書XBRLから全社ぶん決定論抽出する。

**まず1年分**で「コスト・出力品質・DB構成・処理方式」を評価し、そのあと5年分へ広げる。

## 2. 確定した事実（実測）

推測ではなく実際に叩いて確認したもの。**ここを疑う必要はない**。

| 項目 | 実測値 |
|---|---|
| EDINET API v2 | **無料。ただしサブスクリプションキー必須**（無しは401）。旧v1は403で廃止 |
| キーの置き場 | `.env.local` の `EDINET_API`（`.gitignore` の `.env*` で除外済み・git未追跡） |
| 有報zip | **平均710KB**（3,826社実測）。展開後は約7MB／29ファイル |
| 1年分の総量 | 3,826書類 ≒ **3.22GB**（層1の出力は47MB） |
| 処理速度 | **2.05秒/社**（レート制限込み）→ 1年分で**約2.2時間**（実測130.6分） |
| 時間の内訳 | 待機500ms（こちらのレート制限）／DL約1,460ms／**解析39ms**。時間の98%は通信 |
| 再実行 | zipはキャッシュに残るので**通信ゼロ**。全社の再抽出は約2.5分（39ms×3,826） |
| 1日の書類数 | 400件前後。うち**上場企業の有報は数件**（大半は臨時報告書・大量保有報告書・投信） |
| 提出の偏り | 6月に集中（3月決算が大半）。6/1〜7/10だけで **2,196件** |
| 対象の絞り込み | 全書類80,976件 → 有報10,204 → 上場のみ3,783 → XBRL有3,779（非上場6,421を除外） |
| GCS保管料 | 2.7GB ≒ **月¥5〜30**。層1の全社取り込みはインフラ費用として実質ゼロ |

> 費用の結論: **層1の全社展開は金銭コストがほぼ発生しない**。制約は費用ではなく品質担保（§5）。

## 3. 実装済みのもの

```
scripts/edinet/
  client.py   EDINET API v2 クライアント（一覧・zip取得）
  parse.py    XBRL → 層1ファクトの決定論抽出（全社対応）
  batch.py    一括取り込み＋カバレッジレポート（#136）
```

`batch.py` の設計上の約束:

- **再開できる** — 3,900件を最初からやり直せない。処理済みの docID を台帳
  （`_coverage.jsonl`・追記のみ・書くたびに flush）に残し、2回目以降は飛ばす
- **配信ディレクトリには書かない** — 出力先は `data/facts-corpus/`（gitignore 済み）。
  `agent/data/facts/` は人が確認した数値だけを置く場所なので混ぜない（§6-2）
- **重複は「提出が新しい方」を採る** — §5-4 を参照

### 出典（#136 で埋めた）

抽出したファクトは当初 `source_url` が空で、**出典リンクを出せなかった**。
「出典つきで公式資料と一致する数字」が製品価値なので、これでは使えない。

書類の**公開PDF**が鍵無しで引けることを確認して埋めた（推測ではなく実際に叩いた）:

```
https://disclosure2dl.edinet-fsa.go.jp/searchdocument/pdf/<docID>.pdf
  実在する docID → 200 / application/pdf / 845KB
  架空の docID  → 404
```

`FactCard.toDocHref` は `http(s)://` をそのまま返す（`gs://` だけ署名URLに変換する）ので、
フロントの変更は要らなかった。

出典の表示名も整えた。一覧APIの `docDescription` は
`有価証券報告書－第78期(2025/04/01－2026/03/31)` の形で正確だが出典チップには冗長なので、
`periodEnd` から **`2026年3月期 有価証券報告書`** に組み替える（人手で入れた既存データの表記と揃う）。

`client.py` の設計上の約束:

- **キャッシュ優先** — 一度落としたzipと書類一覧は再取得しない。何度も流し直すので再実行が安いことが前提
- **レート制限** — 官公庁の公開APIなので既定 0.5秒間隔
- **失敗しても止めない** — 1社の失敗で全体を落とさず理由を記録して次へ（どの企業がなぜ取れないかがカバレッジ評価そのもの）

`parse.py` で、1社専用版（旧 `scripts/extract_facts_xbrl.py`・**#134 で削除**）から
一般化するために解いたこと:

1. **セグメントのハードコード廃止** — メンバー名は企業ごとに違う（`jpcrp030000-asr_E05137-000...Member` と提出者IDが接頭辞に入る）。文脈IDから自動検出し、日本語名は同梱の `_lab.xml` から引く＝**表示名も推測しない**
2. **集計メンバーの除外** — `ReportableSegmentsMember`（合計）/ `NonConsolidatedMember`（単体）/ 調整額を事業として数えると二重計上になる
3. **セグメント損益の実態対応** — 営業利益ではなく**経常利益**でセグメント開示する企業が実在した（実データで発見）

> **ハマりどころ1**: ラベル定義と文脈IDで区切り文字が違う（ラベル=`-000_Mobile…` / 文脈=`-000Mobile…`）。
> `bare_member()` に正規化を集約してあるので、**両側で必ずこの関数を使う**こと。片方だけ直すとセグメントが静かに0件になる。
>
> **ハマりどころ2**: 報告セグメントの接尾辞は**単複の揺れがある**
> （ハークスレイ等は複数形 `ReportableSegmentsMember`、日立は単数形 `ReportableSegmentMember`）。
> 片方で決め打ちすると、**ラベルは取れているのにセグメントだけ0件**という分かりにくい落ち方をする。
> `_strip_segment_suffix()` を必ず通すこと。実測では日本基準側でもファクトが956→1,052件（+10%）増えた。

## 4. 検証できたこと

**ハークスレイ（7561）の手検証済み `facts.json` と突合**:

```
一致 8 / 不一致 0 / 未抽出 17
```

**不一致ゼロ**。決定論抽出は値を間違えない、という仮説の最初の実証。
未抽出17件の内訳も特定済み:

| 原因 | 件数 | 備考 |
|---|---|---|
| slug の命名差 | 12 | `takeout_lunch`（手作業）vs `takeout_lunch_business`（自動）。**値も事業も同一**、キー名だけが違う |
| EPSがXBRLに無い | 2 | `BasicEarningsLossPerShare` の出現が0回。別要素名の調査が必要 |
| マップ未登録 | 3 | `GrossProfit`(4回) / `DividendPaidPerShareSummaryOfBusinessResults`(5回) は**XBRLに存在する** |

### 百万円は「切り捨て」（#132 で発見・修正）

**日本の開示は百万円単位を切り捨てで表示する。** 四捨五入すると会社自身の資料と1ずれる。

実測（ヴィス 5071）:
```
営業利益 1,915,894,000円 → 説明資料は 1915百万円（切り捨て）
                            四捨五入だと 1916 ＝ 出典と食い違う
```

「**出典つきで公式資料と一致する数字**」が製品価値なので、丸め方は慣行に合わせる。
最初は `round()` で実装しており、ヴィスとの突合で3件の不一致が出て気づいた
（ハークスレイは端数がたまたま同じ側に丸まるため一致していて、**n=1では発見できなかった**）。

### 1年分バッチの実測（#136・2025-08-01〜2026-07-31）

```
対象書類      3,826        抽出成功  3,826 (100.0%)   抽出0件  0
銘柄数        3,815        取得量    3.22 GB          所要   130.6分 / 2.05秒/社
会計基準      jp 3,528 (92.2%) / ifrs 298 (7.8%)
連結/単体     連結 3,317 (86.7%) / 単体のみ 509 (13.3%)
ファクト数    平均15.0 / 中央値16 / 最小2 / 最大58 / 総数 57,351
セグメント    2,577社 (67.4%)・のべ 7,794事業
出典URL       57,351件 (100%)
```

**失敗ゼロ**。60社試走では6社（10%）が「単体決算のみ」で落ちていたので、#131〜#133 の効果。

**人手検証データとの突合（ハークスレイ 7561）**:

```
一致 20 / 不一致 0 / 抽出側に無し 5
```

**不一致ゼロ**。ユーザーが四季報でも別途照合し一致を確認済み。
これは §6-3「検証済みの定義」の直接の根拠になる（3,900社を人手検証はできないが、
抽出器が人手検証済みデータを完全に再現するなら、検証すべきは企業ではなく抽出器）。
抽出側に無い5件は `gross_profit`×2 / `eps`×2 / `dividend_per_share`×1 ＝**マップ未登録**で、
値が違うのではなく取りに行っていない。

### 「抽出成功100%」は実態より良く見える（指標ごとに出す）

**成功=「1件でも取れた」でしかない。** 指標ごとに数え直すと穴が見える:

| 指標 | 取得率 | 欠落の内訳 |
|---|---|---|
| `ordinary_profit` | 100.0% | — |
| `operating_profit` | 97.0% | 115社（連結114） |
| `revenue` | **92.6%** | 284社（jp 255 / ifrs 29） |
| `net_income` | **86.7%** | 509社 → **508社が単体決算** |

いずれも**値の誤りではなく、要素名がマップに無い**（実物で確認済み）:

- **`net_income` は単一原因** — `ProfitLossAttributableToOwnersOfParent`（親会社株主に帰属する
  当期純利益）は連結の概念で、単体決算には存在しない。単体は `ProfitLoss`。
  欠落509社のうち508社が単体決算というきれいな1対1対応。
- **`revenue` は業種依存** — 銀行は経常収益、航空・サービス業は営業収益、IFRS商社は収益と、
  売上高に当たる要素名が業種で違う。実物で確認:
  `8383 鳥取銀行` / `9204 スカイマーク` / `8053 住友商事` はいずれも
  **経常利益・純利益は正しく取れていて売上高だけが無い**（ラベルも 8053 は「税引前利益」と
  IFRSの表記で正しい）。

> **数値は間違っていない。取りに行っていないだけ。** この区別が保てているのは、
> 推測で埋めず「無ければ出さない」を守っているから。

対処は **#146** に分離した（`ProfitLoss` の登録で509社、業種別の売上高要素で284社に効く見込み）。
**この穴が見えたこと自体がカバレッジレポートの成果**なので、レポートの実装（#136）とは分ける。
zipがキャッシュ済みなので、マップを足してからの全社再抽出は**通信ゼロ・約2.5分**で回る。

**60社バッチ**:

```

→ **#133 適用後は 60/60 社（100%）**。連結54社 / 単体のみ6社。ファクト合計956件。

浅香工業・赤阪鐵工所・ディーエムエス・中日本興業・細谷火工・阪神内燃機工業。
いずれも**連結子会社を持たない企業**で、数値は無次元の `CurrentYearDuration` ではなく

## 5. 検証できていないこと（着手前に潰す）

**この4つを潰す前に1年分を回さないこと。** 誤ったラベルのデータを3,900社ぶん作ってから直すのは高くつく。

### 5-1. ~~IFRS採用企業を1社も検証していない~~ → **#132 で完了**

要素名（`RevenueIFRS` 等）は結果的に正しかったが、**判定ロジックが壊れていた**。

> **要素の「存在」で会計基準を判定してはいけない。**
> IFRS採用企業でも、有報の**親会社単独（単体）の財務諸表は日本基準**で作られる。
> そのため IFRS 企業の XBRL にも `NetSales` 等が単体文脈に存在する。
>
> 実測（武田薬品 4502）:
> ```
> NetSales    @ CurrentYearDuration_NonConsolidatedMember =   591,604百万円 ← 単体
> RevenueIFRS @ CurrentYearDuration                       = 4,505,720百万円 ← 連結の実数
> ```
> 存在だけで見て「日本基準」と誤断定し、**親会社単独の59万百万円を全社の売上高として
> 出力**していた。値の捏造ではないが**意味がまったく違う数字**。

`detect_basis()` で**会計基準と連結/単体を同時に**判定するようにした
（この2つは「どのタグ群が主たる財務諸表を担っているか」という同じ問いで、
分けたことが事故の原因だった）。

**IFRSでも要素名は一つではない**: KDDIは `RevenueIFRS` ではなく `NetSalesIFRS`
（6,071,915百万円）を使っていた。同義なので同じ `metric_key` に寄せている。

検証（IFRS採用9社を実物で確認）:
```
4502 武田薬品   4,505,720百万円     6501 日立     10,586,781百万円
6098 リクルート  3,697,351百万円     6702 富士通    3,502,971百万円
7741 HOYA      947,749百万円     9433 KDDI     6,071,915百万円
```
うち OLC / SMC / 東京エレクトロンは実際に日本基準で、正しく `jp` と判定された。

### 5-2. ~~「連結」フラグを無条件 true にしている~~ → **#133 で完了**

`detect_consolidated()` で判定するようにした。

> **判定基準を間違えないこと。** 「`_NonConsolidatedMember` が有るか」では判定できない。
> **連結企業も有報に単体諸表を載せる**ため両方の文脈を持つ（実測: ハークスレイは
> 無次元14件・単体文脈6件）。正しい基準は「**無次元の文脈にヘッドラインの値が入っているか**」。

- 無次元に値がある → 連結（単体文脈は参考として併載されているだけ）
- 無い＆単体側にある → 単体のみ。文脈IDの接尾辞を切り替えて抽出し `consolidated: false`
- どちらにも無い → **None を返して推測しない**（`NO_VALUES` として記録）

**副次効果**: 単体決算のみの企業（実測10%）は誤ラベル以前に**1件も取れていなかった**ので、
これでカバレッジが 54/60 → **60/60** になった。

### 5-3. ~~失敗社を分類していない~~ → **#131 で完了**

`FailReason`（StrEnum）で分類するようにした。**対処が異なるものは別の値にする**という
基準で4分類:

| 値 | 意味 | 対処 |
|---|---|---|
| `public_xbrl_なし` | zip に PublicDoc の .xbrl が無い | 取得側の問題 |
| `会計基準_判定不能` | 日本基準にもIFRSにも該当要素が無い | #132 の候補 |
| `単体決算のみ` | 連結を作らない企業。値は単体側にある | **#133 で解決** |
| `該当タグに数値なし` | 基準は判ったが値が取れない（真の未対応） | 個別調査 |

60社での実測は `単体決算のみ` 6社のみ。**「0件でした」で片付けていたら、
全体の1割が単一の原因で落ちている事実に気づけなかった**。

### 5-4. ~~5年分に向けた重複ルールが無い~~ → **#136 で実装（新しい提出が勝つ）**

同じ決算期の数値が**2つの有報に載る**（FY2025はFY2025とFY2026の両方の有報に）。

**採用するのは提出日が新しい方**（`batch.merge_facts`）。訂正や表示組替を経た数字が
会社自身の最新の見解であり、訂正有報という制度がある以上、古い方を正とする理由が無い。
訂正有報（`docTypeCode` 120以外）を取り込む場合も同じ規則で吸収される。

キーは **（指標 × 期 × 実績/予想 × 連結区分）**。提出日→URLの順に並べてから最後を採るので、
**処理順に依存せず結果が決まる**（再開して順序が変わっても同じ）。
どの書類から来たかは `source_url` と `source_submitted_at` に残るので採用の経緯を追える。

> 1年分では重複は起きない（1社1書類）。5年分に広げたときに効く規則を、
> **先に入れて単体で検証してある**（ネットワーク不要で再現できる）。

## 6. 未決の設計判断

### 6-1. ~~セグメントの slug 命名~~ → **#134 で決定（自動生成に統一）**

**`metric_key` は識別子であって表示名ではない。** 画面にもLLMのデータシートにも出るのは
`metric_label_ja`（`_lab.xml` 由来の「中食事業（売上高）」）なので、slug の読みやすさは
実は誰にも影響しない。3,900社を手で命名することはできない以上、自動が正になる。

移行コストは実測でほぼゼロだった:

| 確認したこと | 結果 |
|---|---|
| slug 文字列をハードコードしている箇所 | **0件**。参照はすべて構造的（`startswith("segment.")` / `endswith(".revenue")`） |
| ゴールデンセット | 事業名（日本語）で問い合わせており slug に非依存 |
| 派生指標の表示名 | 分子の `metric_label_ja` から組む（`_derived_label`）ので slug 非依存 |
| `facts.json` の書き換え | 7561 の12行のみ。**キー名だけ**を置換し、値のフィンガープリントが不変であることを検証 |

```
segment.takeout_lunch.        -> segment.takeout_lunch_business.
segment.store_asset_solution. -> segment.store_asset_and_solution_business.
segment.logistics_food.       -> segment.logistics_food_processing_business.
```

**旧 `scripts/extract_facts_xbrl.py` は削除した。** 手書きslugを再生成するため、
残すと再実行で移行が巻き戻る。加えて `round()`（§4の切り捨て問題）・IFRS非対応・
連結決め打ちと、既に直した不具合を丸ごと抱えていた。出力schemaは `parse.py` と同一で、
能力は完全に上位互換なので失うものは無い。

**slug の安定性（#134の要件）**: `_slug()` はメンバー名だけから決まる純関数なので、
同じ有報を何度流しても同じ slug になる。ただし**切り詰めが一意性を壊す**経路があったので塞いだ:

> 60文字上限で先頭を残すだけだと、先頭が同じ長い事業名を持つ2事業が同一キーに潰れ、
> **別の事業の数値が静かに混ざる**。231社の実測では衝突0件だが、既に上限に達した企業が居る
> （5941 中西製作所＝`..._general_commercial_kitchen_equipm` で "equipment" が途中で切れている）。
> 3,900社では起こりうるので、切り詰める場合は元の名前の SHA-1 先頭6桁を付けて一意にする。
> 組み込み `hash()` は実行ごとに変わる（`PYTHONHASHSEED`）ので使わない。

実測（231社・567セグメント）: 衝突 **0件** / 切り詰め発生 **1件**。
`ＳＰＥ`/`ＧＡ`/`ＦＴ`（7735 SCREEN）のような2〜3文字 slug は発行体自身の略称で、正常。

### 6-2. ~~保存先（DB構成）~~ → **#135 で決定**

**結論: 配信は「1社1ファイルのJSON」、全社コーパスは配信経路に置かない。**

まず実測した（キャッシュ済み231社を実際に抽出し、3,900社ぶんに合成して計測）:

| 項目 | 実測 |
|---|---|
| 1社あたり | **17.0ファクト / 10.3KB** |
| 3,900社の合計 | **66,435件 / 40MB**（Issue の見積もり34MBとほぼ一致） |
| 単一ファイルのパース | **429ms** |
| 1社1ファイルにした場合 | 8.3KB / **0.10ms** ＝ **4,451倍速い** |
| `/c/` ページ1枚 | **180KB**（HTML+RSCペイロード）→ 3,900ページなら **685MB** |

**発見した本当の問題は容量ではなく、エージェントがキャッシュを持っていなかったこと。**
`facts_store._load()` はクエリのたびにファイル全体を読み直していた。

呼び出し回数は**推定せず実測した**（`_load` に計数を挟んで harux のゴールデンセット17問を通す）:

| 呼び出し元 | 1問あたり |
|---|---|
| `query_facts` | 4.2回 |
| `summary` | 2.5回 |
| `doc_label_for_url` | 2.2回（**層2の引用1件につき1回**呼ばれる） |
| **合計** | **9.0回** |

41件なら誤差だが、40MBでは 9.0 × 429ms ＝ **1問あたり約3.9秒**の純粋な無駄になる
（gemini-3のthinking最小化で先頭トークンを24→12秒に縮めた努力を、丸ごと打ち消す量）。

> コードを読んだだけでは「1問3回」に見える（`summary` + `query_facts`×2）。
> 実際に9回なのは、`doc_label_for_url` が検索結果のパッセージごとに呼ばれるため。
> **静的に数えると3倍見誤る。**

採用しなかったもの:

- **Cloud SQL** — 40MBのために常時起動DBを持つと月数千円。他の全コスト（月¥5〜30）を飲み込む
- **BigQuery** — 分析ストアであって**点引きのストアではない**。層1の参照は「ティッカー1件→17件」
  という完全なキー引きで、ここにネットワーク往復（数百ms×3）を挟むと単一ファイル方式より遅くなる。
  ローカル開発にGCP認証が要るようになる副作用もある。`ir_analytics` とは用途が違う

**1社1ファイルの理由は速度だけではない。** 層1は「人が確認した数値だけを出す」原則なので、
企業の追加は1社ずつ人が通す運用になる。1社=1ファイルなら、その追加が
**レビューできる1ファイルの差分**になる（単一ファイルへのマージだと差分が読めない）。
これは 6-3 の「検証済み」の定義（案3）をそのまま運用に落としたもの。

**全社コーパス（3,900社・40MB）は git にも配信イメージにも置かない。**
バッチ（#136）の出力先は GCS（月¥5〜30）。再実行のたびに40MBが git 履歴に永久に積もるのを避ける。
**企業を1社「昇格」させる ＝ GCSから `agent/data/facts/<ticker>.json` にコピーして人が確認する**、
という手順が検証ゲートそのものになる。

**`generateStaticParams` は今のままでよい。** `companies.ts` の `datastoreId` が**必須**なので、
Discovery Engine のデータストアを作らずに企業を足すことはできない＝3,900社は構造的に入らない。
「3,900ページ」「トップの検索/絞り込み」は、**非顧客企業も配信するかどうか**という
まだ決めていない判断（下記）の下流にある。

> **未決（#135のスコープ外）: 非顧客企業の `/c/<ticker>` を公開するか。**
> 公開するなら 685MB の静的出力・トップの検索UI・`datastoreId` の任意化が要る。
> ただし `publishOfficialQa` の考え方（「公式」は発行体の承認を含意する・#124）に照らすと、
> 承認のない3,900社を「公式Q&A」として出すのは筋が悪い。今回の設計はどちらも塞いでいない。

### 6-3. 「検証済み」の定義

`CLAUDE.md` は「層1は検証済み実値のみ・捏造禁止」、取り込み手順は人手検証前提。
**3,900社を人手検証はできない**。取りうる道:

1. **抽出器の検証をもって検証済みと見なす**（本命）— XBRLは提出企業の正本で、LLMを通さずタグから読むだけ。抽出ロジックのゴールデンテストを作れば企業数に依存せず正しさを主張できる
2. サンプル抽出で精度を測り閾値で通す
3. 層1は全社入れるが**公開は検証済み企業だけ**に留める（`publishOfficialQa` が既にそう動く）

## 8. 安全性（試して戻せるか）

- **層1データ** — `agent/data/facts/` は git 管理下。`git revert` で完全に戻る
- **本番** — Cloud Run に旧リビジョンが残っており、再ビルド無しでトラフィックを戻せる
- **AIへの露出** — `publishOfficialQa` が**既定 false**。取り込んで `companies.ts` に足しても、
  フラグを立てない限り noindex ＋ robots.txt で Disallow ＋ JSON-LD 無し ＋ sitemap/llms.txt 非掲載。
  **取り込んでもAIには一切出ない**ので、確認してから公開できる
- **戻せないもの** — AIクローラーが取得済みのコピー。`meta-externalagent` が実際に来ている実績があるため、
  公開フラグを立てる前に必ず値を確認すること

## 9. ローカルでの動かし方

```bash
# キーは .env.local の EDINET_API（値をログに出さないこと）
uv run python -c "
import sys; sys.path.insert(0,'scripts')
from datetime import date
from pathlib import Path
from edinet.client import EdinetClient, load_api_key
from edinet.parse import extract
c = EdinetClient(load_api_key(), Path('data/edinet-cache'))
for d in c.iter_annual_reports(date(2026,6,25), date(2026,6,25)):
    zp = c.fetch_zip(d.doc_id)
    r = extract(EdinetClient.read_public_xbrl(zp), zp, ticker=d.ticker, doc_label=d.doc_description)
    print(d.ticker, d.filer_name, r.standard, len(r.facts), 'facts')
    break
"
```

キャッシュは `data/edinet-cache/`（`.gitignore` 済み・再取得可能）。
zipと書類一覧が溜まるので、消しても動作に影響はない（再取得されるだけ）。
