# EDINET 全社取り込み — 作業ドキュメント

層1（数値）を EDINET API から全上場企業ぶん取り込むための作業メモ。
**次に触る人（人でもAIでも）がここだけ読んで続けられる**ことを目的にする。

設計の背骨は `../CLAUDE.md`、全体設計は `ARCHITECTURE.md`、現状は `HANDOFF.md`。

---

## 1. 何のためにやるか

いま層1（`agent/data/facts.json`）が点いているのは **2社だけ**（7561=31件 / 5071=10件）。
これを EDINET の有価証券報告書XBRLから全社ぶん決定論抽出する。

**まず1年分**で「コスト・出力品質・DB構成・処理方式」を評価し、そのあと5年分へ広げる。

---

## 2. 確定した事実（実測）

推測ではなく実際に叩いて確認したもの。**ここを疑う必要はない**。

| 項目 | 実測値 |
|---|---|
| EDINET API v2 | **無料。ただしサブスクリプションキー必須**（無しは401）。旧v1は403で廃止 |
| キーの置き場 | `.env.local` の `EDINET_API`（`.gitignore` の `.env*` で除外済み・git未追跡） |
| 有報zip | **平均703KB**（60社実測）。展開後は約7MB／29ファイル |
| 1年分の総量 | 3,900社 × 703KB ≒ **約2.7GB** |
| 処理速度 | **1.44秒/社**（レート制限込み）→ 1年分で**約1.6時間** |
| 1日の書類数 | 400件前後。うち**上場企業の有報は数件**（大半は臨時報告書・大量保有報告書・投信） |
| 提出の偏り | 6月に集中（3月決算が大半）。6/1〜7/10だけで **2,196件** |
| GCS保管料 | 2.7GB ≒ **月¥5〜30**。層1の全社取り込みはインフラ費用として実質ゼロ |

> 費用の結論: **層1の全社展開は金銭コストがほぼ発生しない**。制約は費用ではなく品質担保（§5）。

## 3. 実装済みのもの

```
scripts/edinet/
  client.py   EDINET API v2 クライアント（一覧・zip取得）
  parse.py    XBRL → 層1ファクトの決定論抽出（全社対応）
```

`client.py` の設計上の約束:

- **キャッシュ優先** — 一度落としたzipと書類一覧は再取得しない。何度も流し直すので再実行が安いことが前提
- **レート制限** — 官公庁の公開APIなので既定 0.5秒間隔
- **失敗しても止めない** — 1社の失敗で全体を落とさず理由を記録して次へ（どの企業がなぜ取れないかがカバレッジ評価そのもの）

`parse.py` で、1社専用版（`scripts/extract_facts_xbrl.py`）から一般化するために解いたこと:

1. **セグメントのハードコード廃止** — メンバー名は企業ごとに違う（`jpcrp030000-asr_E05137-000...Member` と提出者IDが接頭辞に入る）。文脈IDから自動検出し、日本語名は同梱の `_lab.xml` から引く＝**表示名も推測しない**
2. **集計メンバーの除外** — `ReportableSegmentsMember`（合計）/ `NonConsolidatedMember`（単体）/ 調整額を事業として数えると二重計上になる
3. **セグメント損益の実態対応** — 営業利益ではなく**経常利益**でセグメント開示する企業が実在した（実データで発見）

> **ハマりどころ1**: ラベル定義と文脈IDで区切り文字が違う（ラベル=`-000_Mobile…` / 文脈=`-000Mobile…`）。
> `bare_member()` に正規化を集約してあるので、**両側で必ずこの関数を使う**こと。片方だけ直すとセグメントが静かに0件になる。
>
> **ハマりどころ2**: 報告セグメントの接尾辞は**単複の揺れがある**
> （ハークスレイ等は複数形 `ReportableSegmentsMember`、日立は単数形 `ReportableSegmentMember`）。
> 片方で決め打ちすると、**ラベルは取れているのにセグメントだけ0件**という分かりにくい落ち方をする。
> `_strip_segment_suffix()` を必ず通すこと。実測では日本基準側でもファクトが956→1,052件（+10%）増えた。

## 4. 検証できたこと

**ハークスレイ（7561）の手検証済み `facts.json` と突合**:

```
一致 8 / 不一致 0 / 未抽出 17
```

**不一致ゼロ**。決定論抽出は値を間違えない、という仮説の最初の実証。
未抽出17件の内訳も特定済み:

| 原因 | 件数 | 備考 |
|---|---|---|
| slug の命名差 | 12 | `takeout_lunch`（手作業）vs `takeout_lunch_business`（自動）。**値も事業も同一**、キー名だけが違う |
| EPSがXBRLに無い | 2 | `BasicEarningsLossPerShare` の出現が0回。別要素名の調査が必要 |
| マップ未登録 | 3 | `GrossProfit`(4回) / `DividendPaidPerShareSummaryOfBusinessResults`(5回) は**XBRLに存在する** |

### 百万円は「切り捨て」（#132 で発見・修正）

**日本の開示は百万円単位を切り捨てで表示する。** 四捨五入すると会社自身の資料と1ずれる。

実測（ヴィス 5071）:
```
営業利益 1,915,894,000円 → 説明資料は 1915百万円（切り捨て）
                            四捨五入だと 1916 ＝ 出典と食い違う
```

「**出典つきで公式資料と一致する数字**」が製品価値なので、丸め方は慣行に合わせる。
最初は `round()` で実装しており、ヴィスとの突合で3件の不一致が出て気づいた
（ハークスレイは端数がたまたま同じ側に丸まるため一致していて、**n=1では発見できなかった**）。

**60社バッチ**:

```
抽出成功 54/60（90%）  失敗6社はすべて「数値0件」＝誤った値は出ていない
ファクト数  平均16.2 / 中央値16 / 最小6 / 最大32
セグメント  平均2.2事業（0件13社＝単一事業）
```

**失敗の分類（#131 で実施）**: 6社すべてが `単体決算のみ`。

```
抽出成功        54社
単体決算のみ     6社 (10%)
```

→ **#133 適用後は 60/60 社（100%）**。連結54社 / 単体のみ6社。ファクト合計956件。

浅香工業・赤阪鐵工所・ディーエムエス・中日本興業・細谷火工・阪神内燃機工業。
いずれも**連結子会社を持たない企業**で、数値は無次元の `CurrentYearDuration` ではなく
`CurrentYearDuration_NonConsolidatedMember` 側に入っていた（実物のXBRLで確認済み。
例: 5962=8,358百万円 / 9782=30,308百万円）。

> **#131 と #133 は同じ根**だった。単体決算のみの企業は「連結として誤ラベルされる」
> 以前に**そもそも1件も取れていない**。#133 を解くと同時に、取りこぼしていた
> 全体の**1割**が拾えるようになる。IFRS未対応（#132）とは無関係だった。

## 5. 検証できていないこと（着手前に潰す）

**この4つを潰す前に1年分を回さないこと。** 誤ったラベルのデータを3,900社ぶん作ってから直すのは高くつく。

### 5-1. ~~IFRS採用企業を1社も検証していない~~ → **#132 で完了**

要素名（`RevenueIFRS` 等）は結果的に正しかったが、**判定ロジックが壊れていた**。

> **要素の「存在」で会計基準を判定してはいけない。**
> IFRS採用企業でも、有報の**親会社単独（単体）の財務諸表は日本基準**で作られる。
> そのため IFRS 企業の XBRL にも `NetSales` 等が単体文脈に存在する。
>
> 実測（武田薬品 4502）:
> ```
> NetSales    @ CurrentYearDuration_NonConsolidatedMember =   591,604百万円 ← 単体
> RevenueIFRS @ CurrentYearDuration                       = 4,505,720百万円 ← 連結の実数
> ```
> 存在だけで見て「日本基準」と誤断定し、**親会社単独の59万百万円を全社の売上高として
> 出力**していた。値の捏造ではないが**意味がまったく違う数字**。

`detect_basis()` で**会計基準と連結/単体を同時に**判定するようにした
（この2つは「どのタグ群が主たる財務諸表を担っているか」という同じ問いで、
分けたことが事故の原因だった）。

**IFRSでも要素名は一つではない**: KDDIは `RevenueIFRS` ではなく `NetSalesIFRS`
（6,071,915百万円）を使っていた。同義なので同じ `metric_key` に寄せている。

検証（IFRS採用9社を実物で確認）:
```
4502 武田薬品   4,505,720百万円     6501 日立     10,586,781百万円
6098 リクルート  3,697,351百万円     6702 富士通    3,502,971百万円
7741 HOYA      947,749百万円     9433 KDDI     6,071,915百万円
```
うち OLC / SMC / 東京エレクトロンは実際に日本基準で、正しく `jp` と判定された。

### 5-2. ~~「連結」フラグを無条件 true にしている~~ → **#133 で完了**

`detect_consolidated()` で判定するようにした。

> **判定基準を間違えないこと。** 「`_NonConsolidatedMember` が有るか」では判定できない。
> **連結企業も有報に単体諸表を載せる**ため両方の文脈を持つ（実測: ハークスレイは
> 無次元14件・単体文脈6件）。正しい基準は「**無次元の文脈にヘッドラインの値が入っているか**」。

- 無次元に値がある → 連結（単体文脈は参考として併載されているだけ）
- 無い＆単体側にある → 単体のみ。文脈IDの接尾辞を切り替えて抽出し `consolidated: false`
- どちらにも無い → **None を返して推測しない**（`NO_VALUES` として記録）

**副次効果**: 単体決算のみの企業（実測10%）は誤ラベル以前に**1件も取れていなかった**ので、
これでカバレッジが 54/60 → **60/60** になった。

### 5-3. ~~失敗社を分類していない~~ → **#131 で完了**

`FailReason`（StrEnum）で分類するようにした。**対処が異なるものは別の値にする**という
基準で4分類:

| 値 | 意味 | 対処 |
|---|---|---|
| `public_xbrl_なし` | zip に PublicDoc の .xbrl が無い | 取得側の問題 |
| `会計基準_判定不能` | 日本基準にもIFRSにも該当要素が無い | #132 の候補 |
| `単体決算のみ` | 連結を作らない企業。値は単体側にある | **#133 で解決** |
| `該当タグに数値なし` | 基準は判ったが値が取れない（真の未対応） | 個別調査 |

60社での実測は `単体決算のみ` 6社のみ。**「0件でした」で片付けていたら、
全体の1割が単一の原因で落ちている事実に気づけなかった**。

### 5-4. 5年分に向けた重複ルールが無い

同じ決算期の数値が**2つの有報に載る**（FY2025はFY2025とFY2026の両方の有報に）。
どちらを正とするかのルールが無いと、5年分を入れた瞬間に重複と矛盾が出る。
訂正有報（`docTypeCode` が120以外）の扱いも同じ問題。

## 6. 未決の設計判断

### 6-1. セグメントの slug 命名

自動生成（`takeout_lunch_business`）と既存の手作業（`takeout_lunch`）が食い違う。
**自動に寄せて既存2社を移行する**のが素直だが、`facts.json` を書き換えることになる。
決めてから1年分を回すこと（後から変えると全件再生成）。

### 6-2. 保存先（DB構成）

現在は単一の `agent/data/facts.json`（22KB / 41件）を `fs.readFileSync` で
ビルド時に読んでいる。3,900社 × 平均16件 ≒ **62,000件・約34MB** になる。

- **Cloud SQL は入れない** — 34MBのために常時起動DBを持つと月数千円かかり、他の全コストを飲み込む
- 候補: **ティッカー別JSON**（`data/facts/<ticker>.json`・必要な社だけ読む）／ BigQuery（既に `ir_analytics` で使用中）
- 併せて `generateStaticParams` が全社ぶん静的ページを作る点（3,900ページ）の対処も必要

### 6-3. 「検証済み」の定義

`CLAUDE.md` は「層1は検証済み実値のみ・捏造禁止」、取り込み手順は人手検証前提。
**3,900社を人手検証はできない**。取りうる道:

1. **抽出器の検証をもって検証済みと見なす**（本命）— XBRLは提出企業の正本で、LLMを通さずタグから読むだけ。抽出ロジックのゴールデンテストを作れば企業数に依存せず正しさを主張できる
2. サンプル抽出で精度を測り閾値で通す
3. 層1は全社入れるが**公開は検証済み企業だけ**に留める（`publishOfficialQa` が既にそう動く）

## 8. 安全性（試して戻せるか）

- **層1データ** — `facts.json` は git 管理下。`git revert` で完全に戻る
- **本番** — Cloud Run に旧リビジョンが残っており、再ビルド無しでトラフィックを戻せる
- **AIへの露出** — `publishOfficialQa` が**既定 false**。取り込んで `companies.ts` に足しても、
  フラグを立てない限り noindex ＋ robots.txt で Disallow ＋ JSON-LD 無し ＋ sitemap/llms.txt 非掲載。
  **取り込んでもAIには一切出ない**ので、確認してから公開できる
- **戻せないもの** — AIクローラーが取得済みのコピー。`meta-externalagent` が実際に来ている実績があるため、
  公開フラグを立てる前に必ず値を確認すること

## 9. ローカルでの動かし方

```bash
# キーは .env.local の EDINET_API（値をログに出さないこと）
uv run python -c "
import sys; sys.path.insert(0,'scripts')
from datetime import date
from pathlib import Path
from edinet.client import EdinetClient, load_api_key
from edinet.parse import extract
c = EdinetClient(load_api_key(), Path('data/edinet-cache'))
for d in c.iter_annual_reports(date(2026,6,25), date(2026,6,25)):
    zp = c.fetch_zip(d.doc_id)
    r = extract(EdinetClient.read_public_xbrl(zp), zp, ticker=d.ticker, doc_label=d.doc_description)
    print(d.ticker, d.filer_name, r.standard, len(r.facts), 'facts')
    break
"
```

キャッシュは `data/edinet-cache/`（`.gitignore` 済み・再取得可能）。
zipと書類一覧が溜まるので、消しても動作に影響はない（再取得されるだけ）。
